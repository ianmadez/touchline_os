# Parser reference data

These files are what let the parser turn a career save into readable tables, player names and nationalities. They are committed to this repository deliberately, because a hosted build clones the repo and has no access to anything that is not in it. Without them every table and field decodes as unknown, every player renders as just `#<id>`, and every nationality is a bare number.

Nothing here is generated by this project, with one exception: `meta-index.json`, which is generated FROM the datasheets by `npm run meta:index` and contains no data of its own. Provenance, licensing and the decision to ship the rest are recorded below, so that anyone using or redistributing TouchlineOS can see exactly what they are getting and from where.

## The five FIFA datasheets: `fifa_ng_db-meta-fifa17.xml` to `-fifa21.xml`

Five more t3db meta descriptions, one per game, for the same `fifa_ng_db` database that an FC-era datasheet describes. A career save from FIFA 17 to 21 is the SAME container as an FC-era one, so these files are the whole of the support for those titles: they declare 146 to 187 tables each (against 242 in the FC datasheet), and they are what names `zgrE` as `career_managerhistory` and supplies the bit depth and `rangelow` each field needs.

They are not interchangeable with the FC datasheet, and that is not a technicality. 27 of the table ids the FIFA 18 datasheet declares are absent from the FC one (`career_trophies`, `career_transferoffer`, `career_loanbuy`, `career_boardoutcomes`), and some fields changed identity: the contract date field is `nzON` with an 8-bit range in FIFA 18 and `EBrh` as a 19-bit date from FIFA 20 onwards. Reading a FIFA 18 save with the FC datasheet names tables confidently and decodes their fields from the wrong bit offsets, which produces numbers that look plausible and are not in the save.

**Obtained from:** the `xml/<version>/` folders of [sammygriffiths/fifa-career-save-parser](https://github.com/sammygriffiths/fifa-career-save-parser), whose own description is "Parse PC career mode save files from FIFA 17 - 21".

## `meta-index.json` — 10.8 KB

**This is the one generated file.** For each datasheet it holds the four-character table ids that datasheet declares, and nothing else. A save's own table directory can be read without any datasheet at all, so comparing that list against these sets identifies which game wrote a save in a few milliseconds without loading a single XML file. Only the identified game's datasheet is then read, which keeps a page that opens an FC career from downloading five datasheets it will never use.

Regenerated by `npm run meta:index`, which also fails loudly if a datasheet is missing or unreadable. `npm run meta:index -- --check` asserts it is current, so it cannot drift from the datasheets beside it.

## `fifa_ng_db-meta.xml` — 1.33 MB

The t3db meta description of EA's `fifa_ng_db`. A career save stores four-character shortnames for tables and fields (`biWl`, `uipx`); this file maps them to readable names (`career_managerinfo`, `userid`) and carries the integer `rangelow` offset a bit-packed value is stored relative to. It describes 242 tables and 9,031 fields; the parser reads 26 of those tables and the fields it needs.

**Obtained from:** the `data/` folder of the **fc26companion** project (`srikz4`), which is what `references/fc26companion` in a working copy of this repository is. That project does not state where it obtained the file, and the file itself carries no source comment beyond
`<!--This is the meta XML file for a t3db database.-->`. Its own parser module calls it "the FC 25 meta XML" and notes that it resolves FC 26 fine.

## `playernames_fc26.csv` — 0.71 MB

18,408 rows of `player_id,short_name,long_name`, mapping EA's internal player id — the same id the save stores — to the name to display. The save cannot supply this: it carries only 54 name records of its own (`editedplayernames`), and 14,102 of the 18,926 players in the reference save resolve only through this table.

**Obtained from:** also bundled by **fc26companion**, whose own header records its source:

```
# FC 26 player name table. Names only, by EA internal player_id.
# source: https://raw.githubusercontent.com/ismailoksuz/EAFC26-DataHub/main/data/players.csv
# imported: 2026-08-27T17:56:36.835Z
player_id,short_name,long_name
```

Credit to the authors of [EAFC26-DataHub](https://github.com/ismailoksuz/EAFC26-DataHub), as
fc26companion's own README does.

## `nations_fc26.csv` — 2.3 KB

162 rows of `nation_id,name`, mapping the nationality code a player row carries to the country to display. **This one is NOT extracted from EA's `fifa_ng_db` meta**: the save's `nations` table is not decoded by this parser, so the mapping has to come from outside the save. fc26companion's own header says where it did:

```
# FC 26 nation ids, extracted from the imported player dataset
nation_id,name
```

Spot-checked against the reference save before being relied on: the codes the save's own players carry (14, 36, 42, 7, 27, 54) resolve to England, Norway, Scotland, Belgium, Italy and Brazil, and the mapping is 1:1 for those players' clubs and names.

Deliberately **not** a three-letter code table. Codes such as `ENG`, `DEN` and `DEU` are not published anywhere in this repository or in either upstream dataset, so shipping them would mean inventing them - and an invented abbreviation sitting beside real save data is indistinguishable from a fact the game recorded. What the source table actually carries is country names, so names are what is shown. The save's raw numeric code is stored alongside the name, so a code table or a flag set can be added later without re-reading anyone's save.

## Licensing — what was checked, and the decision taken

Checked 2026-10-05, at source, not assumed:

| Project | Licence |
|---|---|
| `fc26companion` (the FC datasheet, name table and nation table came from here) | MIT (`Copyright (c) 2026 srikz4`) **with an added paragraph that narrows the grant**: *"This license covers the Companion source code only; it does not grant any rights over game data or third-party assets."* |
| `ismailoksuz/EAFC26-DataHub` (upstream of the name table) | **none** — no `LICENSE` file, and the GitHub API reports no licence. No rights granted. |
| `sammygriffiths/fifa-career-save-parser` (the five FIFA datasheets) | **ISC declared in `package.json`**, and stated as ISC in its README. There is no `LICENSE` file in the repository, so the grant rests on that declaration, which is the npm convention and is a real grant. |
| `GioAc96/fc-cm-web-parser` | **none** — no rights granted. |

The chain is EA game data → EAFC26-DataHub (grants nothing) → fc26companion (MIT for its source code only, addendum excludes game data) → this repository.

I reviewed that finding and took the decision to commit both files anyway, on the
grounds that a platform without player names and without table names is not usable, and that the alternative which is asking every user to supply their own copy was worse. That decision is recorded here rather than hidden, together with the finding it was made against, so it is a conscious one that can be revisited. Anyone forking this repository inherits it and should make their own call.

## How these files are used

| Runtime | How it reads them |
|---|---|
| Local (`npm run dev`) | From this folder directly, via `src/lib/platform/parse-resources.ts`. `FC_META_XML` / `FC_NAME_TABLE` / `FC_NATION_TABLE` override the paths. The index and the datasheets are read on demand, so a save only costs the one datasheet it is read with. |
| Browser (`npm run build:browser`) | `out-browser/` is a static site, so the page fetches them from `/parse-resources/…` — this folder is served as-is. `scripts/with-target.mjs` fails the build loudly if any of the three is missing. The index and the FC datasheet are fetched at page load and the other datasheets by URL as they are needed. |

Only the facts the parser names are used. The whole file is carried because it is the artefact both runtimes resolve and because a partial extract would have to be regenerated and re-verified every time the parser reads one more field. If that changes, the replacement plan is a small first-party datasheet
of the 26 tables and 205 (table, field) facts actually read — about 8.9 KB — extracted from this file with a parity test proving the parser produces byte-identical output without it.
