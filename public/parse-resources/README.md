# Parser reference data

These two files are what let the parser turn a career save into readable tables and player names. They are committed to this repository deliberately, because a hosted build clones the repo and has no access to anything that is not in it. Without them every table and field decodes as unknown and every player renders as just `#<id>`.

Nothing here is generated by this project. Provenance, licensing and the decision to ship them are recorded below, so that anyone using or redistributing TouchlineOS can see exactly what they are getting and from where.

## `fifa_ng_db-meta.xml` — 1.33 MB

The t3db meta description of EA's `fifa_ng_db`. A career save stores four-character shortnames for tables and fields (`biWl`, `uipx`); this file maps them to readable names (`career_managerinfo`, `userid`) and carries the integer `rangelow` offset a bit-packed value is stored relative to. It describes 242 tables and 9,031 fields; the parser reads 26 of those tables and the fields it needs.

**Obtained from:** the `data/` folder of the **fc26companion** project (`srikz4`), which is what `references/fc26companion` in a working copy of this repository is. That project does not state where it obtained the file, and the file itself carries no source comment beyond
`<!--This is the meta XML file for a t3db database.-->`. Its own parser module calls it "the FC 25 meta XML" and notes that it resolves FC 26 fine.

## `playernames_fc26.csv` — 0.71 MB

18,408 rows of `player_id,short_name,long_name`, mapping EA's internal player id — the same id the save stores — to the name to display. The save cannot supply this: it carries only 54 name records of its own (`editedplayernames`), and 14,102 of the 18,926 players in the reference save resolve only through this table.

**Obtained from:** also bundled by **fc26companion**, whose own header records its source:

```
# FC 26 player name table. Names only, by EA internal player_id.
# source: https://raw.githubusercontent.com/ismailoksuz/EAFC26-DataHub/main/data/players.csv
# imported: 2026-08-27T17:56:36.835Z
player_id,short_name,long_name
```

Credit to the authors of [EAFC26-DataHub](https://github.com/ismailoksuz/EAFC26-DataHub), as
fc26companion's own README does.

Checked 2026-10-05, at source, not assumed:

| Project | Licence |
|---|---|

| `ismailoksuz/EAFC26-DataHub` (upstream of the name table) | **none** — no `LICENSE` file, and the GitHub API reports no licence. No rights granted. |
| `sammygriffiths/fifa-career-save-parser` | **none** — no rights granted. |
| `GioAc96/fc-cm-web-parser` | **none** — no rights granted. |

The chain is EA game data → EAFC26-DataHub (grants nothing) → fc26companion (MIT for its source code only, addendum excludes game data) → this repository.

I reviewed that finding and took the decision to commit both files anyway, on the
grounds that a platform without player names and without table names is not usable, and that the alternative which is asking every user to supply their own copy was worse. That decision is recorded here rather than hidden, together with the finding it was made against, so it is a conscious one that can be revisited. Anyone forking this repository inherits it and should make their own call.

## How these files are used

| Runtime | How it reads them |
|---|---|
| Local (`npm run dev`) | From this folder directly, via `src/lib/platform/parse-resources.ts`. `FC_META_XML` / `FC_NAME_TABLE` override the paths. |
| Browser (`npm run build:browser`) | `out-browser/` is a static site, so the page fetches them from `/parse-resources/…` — this folder is served as-is. `scripts/with-target.mjs` fails the build loudly if either file is missing. |

Only the facts the parser names are used. The whole file is carried because it is the artefact both runtimes resolve and because a partial extract would have to be regenerated and re-verified every time the parser reads one more field. If that changes, the replacement plan is a small first-party datasheet
of the 26 tables and 205 (table, field) facts actually read — about 8.9 KB — extracted from this file with a parity test proving the parser produces byte-identical output without it.
